

# Beacon Logic Realization in `src/beacon_system/logic`

This document describes how the theoretical Beacon Logic framework is realized in the `src/beacon_system/logic` subsystem. The purpose of this module is not merely to provide auxiliary prompt context, but to operationalize Beacon Logic as an executable reasoning layer that transforms raw task context into structured semantic artifacts. In the current implementation, the logic subsystem acts as the single source of truth for semantic core extraction. It takes normalized task input, performs local and global reasoning under the engineering conditions EC1–EC9, and produces a set of stable downstream artifacts, including Raw Beacon IR, Beacon Tree, Signature Hints, and a minimal Constraint Summary. These artifacts are then consumed by later stages of the system, especially generation and verification.

From an architectural perspective, the logic subsystem is organized as a layered pipeline rather than a monolithic analyzer. The preprocessing stage is implemented in `preprocess.py`, where heterogeneous task fields are normalized into a stable intermediate view. This stage is intentionally non-inferential: it prepares language information, file-level text, body text, target signatures, import-like lines, and related warnings, but it does not yet perform any Beacon reasoning. On top of this normalized representation, `rules_local.py` implements intra-function reasoning, while `rules_global.py` extends the reasoning across function boundaries and global state. The outputs of these two stages are then merged by `builder.py` into a unified Raw Beacon IR, projected into a human-readable tree form by `tree.py`, and supplemented by parameter, call, and return-level hints through `signatures.py`. Finally, `refiner.py` may polish the tree text in a constrained manner without modifying structural facts, and `engine.py` orchestrates the full sequence as the single entry point of the logic pipeline .

The overall execution path of the subsystem directly reflects the staged character of Beacon Logic. `LogicEngine.build()` first invokes preprocessing, then computes local beacons, global beacons, raw IR, beacon tree, signature hints, and optional refinement, before merging all outputs into a stable result object. This design is important because it preserves a strict separation between semantic inference and downstream consumption. In other words, the logic subsystem is not an informal heuristic helper; it is the module where the project’s theoretical commitments are concretely enforced.

At the level of local reasoning, the implementation corresponds closely to the judgment system proposed in the Beacon Logic formulation. The first rule, `L-OUT`, identifies observable output roots inside a function. In the Python path this is implemented through `_PythonFunctionIndex.find_output_nodes()` together with `_is_output_node()`, while in the Java path the same role is played by `_JavaMethodIndex.find_output_nodes()`. The engineering interpretation of observability is deliberately broader than a purely semantic notion of program output: besides `return` and `throw`, the implementation also recognizes `print`, logging operations, and file-write–style side effects. This is the operational realization of EC2, where engineering observability is preferred over narrow theoretical purity.

Once output roots have been identified, the subsystem applies dependency expansion, corresponding to rule `L-DEP`. In Python, dependencies are built through `_build_data_dependencies()` and `_walk_body_with_control()`, and the actual closure is computed by `backward_closure(seed_ids)`. In Java, the same role is implemented with a line-level def-use approximation plus control-dependence heuristics, followed again by backward closure. The crucial point here is that the code does not attempt exact semantic dependence, which would be unrealistic in this setting. Instead, it uses a safe over-approximation that favors coverage over minimality. Data dependencies are approximated by linking variable uses to recent preceding definitions, while control dependencies are modeled through active control constructs such as `if`, `for`, `while`, `try`, and similar nodes. This realizes EC1 and EC3 in a very explicit manner: the subsystem is designed to tolerate redundancy so that core logic is not accidentally omitted.

The next stage of local reasoning implements validation filtering, corresponding to `L-VAL`. Here the code first computes a raw local closure and only then performs heuristic filtering to distinguish core computational logic from validation-oriented scaffolding. In Python this is handled by `filter_validation_nodes(beacon_ids, output_ids)` and `_looks_like_validation()`, while in Java the counterpart is `filter_validation_nodes(...)` together with `_looks_like_java_validation(...)`. Typical validation patterns include null checks, boundary guards, assertion-style conditions, and early-exit branches that serve defensive rather than semantic purposes. Importantly, output nodes themselves are given precedence and are not indiscriminately removed, which prevents the filtering stage from erasing the actual semantic exit points of the function. This is precisely the engineering interpretation of EC4: validation detection is heuristic, conservative, and subordinate to semantic usefulness rather than formal proof.

After filtering, the subsystem applies reduction and normalization through `reduce_nodes`, corresponding to `L-RED`. In both Python and Java, reduction imposes stable ordering, performs whitespace normalization, removes duplicates, and returns a compact sequence of retained node identifiers. This stage is intentionally modest in ambition. It does not attempt semantic compression in a theorem-proving sense; rather, it improves readability, stability, and downstream usability. In that sense, it is the clearest code-level expression of EC5: interpretability is treated as a design goal, even when this means sacrificing some low-level completeness.

These local stages together yield exactly the layered structure described in the theoretical account: a raw beacon closure, a filtered closure, and a reduced local semantic core. In the implementation, this progression is materialized in the fields of `LocalRulesResult`, which records output roots, reduced beacon nodes, filtered validation nodes, and the detailed node list with dependencies, roles, line information, and source text. This result therefore functions as the concrete carrier of the theoretical transition from (B^{raw}) to (B^{flt}) to (B^*) .

Global reasoning extends this local result into a program-aware semantic closure. The first step is the implementation of `G-BASE`, which simply lifts normalized local beacons into the initial global set for each function. In the Python implementation this is done by `_PythonGlobalIndex._seed_local_to_global()`, and in Java by `_JavaGlobalIndex._seed_local_to_global()`. This stage is deliberately simple, because it establishes the seed from which all later global propagation is derived.

Cross-function propagation is then handled by `G-CALL` and `G-RET`. Call linking is indexed through `_index_calls()`, but only when the call-site itself already belongs to a beacon-relevant statement. This is a critical design decision. The system does not blindly inline all callees; it only propagates along semantically relevant call sites. The subsequent fixpoint procedure then pulls the callee’s global beacons back into the caller. This realizes EC6 as selective propagation rather than unrestricted call graph expansion. Return-flow propagation follows the same philosophy. `_index_return_flow()` detects assignments and returns in which a function call contributes to a beacon-relevant value, and the fixpoint stage then extends the caller with the callee’s semantic core. This is the practical realization of EC7: return-flow tracking is intentionally lightweight and engineering-oriented, not a full flow-sensitive interprocedural analysis.

Global state is handled through `G-GLOB` and its symmetric counterpart. In Python, `_index_global_symbols()` collects reads and writes over module-level globals; in Java the same function is applied to class fields through text-level heuristics. During fixpoint propagation, if either a read or a write of a global symbol is already implicated in the beacon set, the subsystem conservatively pulls in the corresponding read/write cluster. This cluster-style propagation is exactly the operational meaning of EC8. The objective is not to perfectly distinguish precise slices of global interaction, but to ensure that stateful dependencies are not lost.

All of this interprocedural reasoning is driven by a single fixpoint loop in `_run_global_fixpoint()`. The loop starts from the `G-BASE` seeds and repeatedly applies call propagation, return-flow propagation, and global-state propagation until no function-level global set grows further. This is one of the strongest points of the implementation, because it shows that the logic subsystem is not simply a bag of ad hoc heuristics. It is, in fact, a rule-driven closure computation whose operational semantics align with the theoretical view of Beacon Logic as a conditioned inference system. The resulting `GlobalRulesResult` records entry functions, local and global beacon node ids for each function, call edges, return-flow edges, global-state edges, and the final program-level beacon node ids, thereby preserving both the closure result and the evidence of how that result was obtained .

The last step of the reasoning pipeline is program-level lifting through `P-ENTRY`. Entry inference is implemented through `_infer_python_entries()` and `_infer_java_entries()`, where `main` is preferred when available, and otherwise public or API-like functions are used as fallback entry points. The program-level beacon set is then defined as the union of the global sets of these entry functions. This realizes EC9 in a flexible way that is compatible with realistic project structures, where semantic entry points may not always be explicit in a purely classical sense.

An important implementation detail is that provenance is preserved all the way into the IR. `builder.py` attaches rule tags such as `L-DEP`, `G-CALL`, `G-RET`, and `G-GLOB` to the corresponding edges, and records the rules used in the provenance metadata. This is more than a debugging convenience. It turns the raw graph structure into an auditable semantic artifact, which is crucial for later tree rendering, downstream verification, and possible future visualization. In other words, the system does not only produce a result; it also records how that result was derived.

The distinction between Python and Java paths should also be understood clearly. The Python implementation is more structurally precise because it operates at AST statement granularity, with node identifiers tied to functions, line numbers, and statement types. This provides stable localization and richer evidence. The Java implementation, by contrast, adopts a lightweight method-block and line-level strategy rather than a full compiler-grade semantic parser. This makes it cheaper and more robust in cross-project use, but also means it is necessarily more heuristic in syntax-heavy or semantically complex cases. This tradeoff is fully consistent with the conditioned formalism of Beacon Logic: the goal is not ideal semantic completeness, but practical semantic core extraction that remains interpretable and stable enough to support LLM-based downstream tasks.

Taken together, the current `src/beacon_system/logic` implementation should be understood as a full engineering realization of Beacon Logic rather than a loose inspiration from it. The subsystem first identifies observable semantic roots, then computes a conservative backward dependency closure, filters validation-oriented branches, reduces the result into a readable local core, lifts that core to the global level, propagates across calls, returns, and global state through fixpoint iteration, and finally projects the result into stable artifacts usable by generation and verification. This pipeline gives executable form to the three judgment levels of the theory—local, global, and program-level—and turns them into concrete, inspectable program semantics.

At the same time, the boundaries of the current implementation should be stated plainly. The Java path remains heuristic rather than compiler-complete; validation filtering depends on pattern quality and may exhibit domain sensitivity; global-state propagation is conservative and can introduce redundancy; and return-flow reasoning is intentionally lightweight. These are not accidental weaknesses but consequences of the chosen engineering conditions. Beacon Logic, as implemented here, is not intended to be a perfect static analyzer. It is intended to be a robust, interpretable, and operational semantic-core extractor that can serve as a stable backbone for LLM-driven code generation and verification. On that criterion, the current implementation already achieves a strong and coherent realization of the theory .
